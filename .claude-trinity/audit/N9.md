## 必修 1 · F2 残留：限购 COUNT 的快照穿透 ✅ 已修

`model/subscription.go:344 countPlanPurchasesTx`

```go
query := DB
if tx != nil {
    query = tx.Clauses(clause.Locking{Strength: "UPDATE"})
}
```

照复验员给的修法做，没有自创第二套方案：

- `tx != nil`（事务内的限购判定）→ 加锁读。`users` 行锁只做到串行化，做不到读最新；
  MySQL 默认 RR 下事务快照由事务内第一条**普通** SELECT 固定，而
  `PurchaseSubscriptionWithBalance` 的第一条是 `loadBalancePayablePlanTx` 的普通 SELECT，
  快照在抢到 `users` 锁之前就已固定，普通 COUNT 会一直读旧快照 → 上限判定通过 → 白拿额度。
- `tx == nil`（`CountPlanPurchases`，controller 下单前预检）→ **保持非锁读**，预检本来就是尽力而为，
  且不能在事务外把订单行锁住。
- 复用既有 `clause.Locking` 写法（同文件 :398 / :531 / :751 已有四处），没有造平行路径。
- 跨三库：GORM sqlite dialector 的 `"FOR"` ClauseBuilder 对 `clause.Locking` 直接 return（已读源码
  `glebarez/sqlite@v1.9.0/sqlite.go:116`），PG 与 MySQL 正常渲染 `FOR UPDATE`。
- 未做 `subscription_orders` 唯一约束 / schema 迁移 —— 按裁决留给 D8。

## 死锁复核 —— ⚠️ 结论不是「无环」，有一条新引入的同用户环，需主控裁决

改动后各路径的锁获取顺序：

| 路径 | 顺序 |
|---|---|
| 回调结算 `CompleteSubscriptionOrder` | `subscription_orders`(trade_no 单行) → `users`(买家) → **`subscription_orders`(user_id=U 区间, 新增)** → `top_ups` → `p3_orders` |
| 余额购买 `PurchaseSubscriptionWithBalance` | `users` → **`subscription_orders`(区间, 新增)** → insert `subscription_orders` |
| 库存码兑换 `service/distribution_transactions.go` | `distribution_inventories` → `users` → **`subscription_orders`(区间, 新增)** |
| `AdminBindSubscription` | `users` → **`subscription_orders`(区间, 新增)** |
| `ExpireSubscriptionOrder` | `subscription_orders`(单行) |

回调链路是 `orders → users`，其余三条是 `users → orders`，**方向本来就是反的**。
改动前这不成环：回调只按唯一索引 `trade_no` 锁单行（RR 下唯一索引等值匹配退化为记录锁、无间隙），
而余额/库存/AdminBind 侧只做 INSERT 新行，两边不争抢同一条既有记录。

改动后 `users → orders` 三条路径新增了对 `subscription_orders` 的**区间加锁读**。
MySQL RR 下 `SELECT ... FOR UPDATE` 走 `user_id` 索引，会对扫到的索引记录加 next-key 锁，
**且不释放不匹配行的锁**（释放是 READ COMMITTED 的行为），所以该用户名下的 pending 单也会被锁住。
由此出现两个真实的环：

1. T1 = 用户 U 的订单 X 的网关回调（持 X，等 `users` U）；T2 = 同一用户 U 的余额购买 /
   库存兑换 / AdminBind（持 `users` U，等区间锁，区间含 X）→ 互等。
2. 同一用户两笔不同 pending 单 X、Y 的回调并发：T1 持 X + `users` U 等 Y，T1' 持 Y 等 `users` U → 互等。

**影响评估**：InnoDB 会毫秒级检测并回滚其一（1213），回调返回错误、订单仍为 pending、网关重试后正常结算；
余额购买返回错误由用户重试。**不丢钱、不重复入账**，是可用性抖动，
量级远小于被修掉的「限购穿透白拿额度」。触发条件是同一用户在毫秒级窗口内跨两条结算路径并发，概率低但非零。

复验意见里「同用户已被 users 行锁串行化 → 不引入新死锁」的推理，只覆盖了同用户余额路径之间，
**没有覆盖回调路径（orders→users）与其余路径（users→orders）的方向反转**，该结论不成立。
我按裁决「只修本轮路径」没有自行改动 `CompleteSubscriptionOrder` 的结构，把选择权交回主控：

- **方案 A（推荐，并入 D8 那轮）**：加 `(user_id, plan_id, status)` 复合索引。
  扫描范围收窄到「该用户该档位的成功单」，pending 单 X/Y 落在别的键区间不再被锁，上面两个环同时消失。
  这本来就是 D8 纵深防御要做的 schema 迁移，一次到位。
- **方案 B**：回调链路改成先无锁读订单拿 `UserId` → 锁 `users` → 再 `FOR UPDATE` 重读订单，
  把全仓统一成 `users → orders`。能彻底消环，但要动结算主路径，需单独一轮评审。
- **方案 C**：接受这个概率极低、网关自带重试兜底的抖动，先上线。
