## 任务 B · 四条购买链路改为直接加余额

统一 seam（复用既有 `tx.Model(&User{}).Update("quota", gorm.Expr("quota + ?", …))` 写法，
与 `model/topup.go:206,434,575,637`、`model/redemption.go:140` 一致，**未新建平行加额度实现**）：

```go
func CreditPlanQuotaTx(tx *gorm.DB, userId int, plan *SubscriptionPlan) (int64, error)
```

职责：档位购买上限校验 → 分组升级 → `users.quota += plan.TotalAmount`，返回实际到账 quota。
缓存同步与付费钩子由调用方在事务提交后执行（`applyPlanPurchaseSideEffects`）。

| 路径 | 入口 | 落地 |
|---|---|---|
| 余额购买 | `PurchaseSubscriptionWithBalance` | 同一事务：`chargeWalletForPlanTx` 扣 `requiredQuota` → `CreditPlanQuotaTx` 加 `plan.TotalAmount` → 建 success 订单。**净额恒 = `TotalAmount - requiredQuota`**；提交后缓存按净 delta 同步 |
| 在线支付 ×5 | `CompleteSubscriptionOrder` | 同一事务：锁单 → `CreditPlanQuotaTx` → `upsertSubscriptionTopUpTx(…, credited)` → 翻 success + 分销投影 |
| 管理员绑定 | `AdminBindSubscription` | 单事务 `CreditPlanQuotaTx`；**不建订单**（与改造前一致） |
| 代理库存码 | `RedeemDistributionInventoryCode` | 原 `CreateUserSubscriptionFromPlanTx` 调用点原地换成 `model.CreditPlanQuotaTx`，仍在原事务内；提交后 `model.InvalidateUserCache` |

全部保留：`UpgradeGroup` 升级、`SyncSubscriptionDistributionOrderTx` 投影、`fireSubscriptionPaidHook`
（管理员绑定改造前后都不触发钩子，未改语义）。

`upsertSubscriptionTopUpTx` 的 `Amount: 0` → `Amount: creditedQuota`（新建与更新两个分支都写）。

`CountUserSubscriptionsByPlan` 签名与函数名不变（5 个支付 controller 依赖，属 N3），
内部改为统计 `subscription_orders` 里该用户该档位的 **success** 订单数；
`CreditPlanQuotaTx` 内的上限校验复用同一个 `countPlanPurchasesTx`。

顺带的结构性整理（都在本轮必改函数内）：`CompleteSubscriptionOrder` 拆出
`loadPendingSubscriptionOrderTx` / `markSubscriptionOrderPaidTx` / `newOrderPurchaseOutcome`，
`PurchaseSubscriptionWithBalance` 拆出 `loadBalancePayablePlanTx` / `chargeWalletForPlanTx` /
`createBalancePurchaseOrderTx`，`trade_no` 列引号逻辑收敛为 `subscriptionTradeNoColumn()`
—— 全部函数 ≤40 行、参数 ≤5。

## 争议点与遗留风险

1. **`TopUp.Amount` 的单位存在歧义（请门下省裁决）**
   契约要求写「实际到账 quota」，已照办。但仓库里这个字段有两种约定：
   - `model/topup.go:195,418,562,626`：`quota = Amount × QuotaPerUnit` → Amount 是**美元数**
   - `model/topup.go:490`（creem）：`quota = Amount` → Amount 就是 **quota**
   - `web/default/src/features/wallet/components/dialogs/billing-history-dialog.tsx:243`
     用 `formatCurrencyFromUSD(record.amount)` 渲染 → 按**美元**显示

   即：写 quota 后，账单历史里一笔 $5 的档位会显示成 `$2,500,000.00`（原来显示 `$0.00`）。
   后端无任何 `SUM(amount)` 聚合，只有展示端受影响。若要显示正确，应写
   `plan.TotalAmount / common.QuotaPerUnit`。**本轮按契约字面写 quota，未擅自改。**

2. **`TaskPrivateData.BillingSource` 保留，与 N1 交接单第 1 条冲突**
   N1 建议随 `SubscriptionId` 一起删；但架构红线 4 与我方任务书只点名删 `SubscriptionId`，
   且红线要求 `billing_source` 保留恒为 `wallet`。已保留字段、改写为
   `service.BillingSourceWallet` 常量（`relay/common.RelayInfo.BillingSource` 已被 N1 删除）。
   现状：Go 侧只写不读（前端读的是 usage log 的 `other.billing_source`，不是任务私有数据）。
   若门下省认定应删，改动面 = `model/task.go:104` + `controller/relay.go:581` 两行。

3. **`plan.TotalAmount <= 0` 的档位会「收钱不发额度」**
   旧语义 0 = 不限量订阅池，新语义下 0 = 到账 0。`CreditPlanQuotaTx` 不报错、只不加额度
   （日志与 `TopUp.Amount` 都会如实记 0）。**上线前必须先把 9 档 `total_amount` 灌好**（D7 迁移工具），
   否则真金白银会打水漂。是否改成硬报错，请主控定。

4. **购买上限口径迁移**：`MaxPurchasePerUser` 从「数 `user_subscriptions` 行」改为「数 success 订单」。
   影响：改造前管理员绑定会占用上限，现在不占（管理员绑定不落订单）。存量数据下上限计数会从
   0 重新开始（旧订阅行不再被计入）—— 需要在公告里说明。

5. **`AdminBindSubscription` 新增了一条 `RecordLog(LogTypeTopup)`**（改造前发放额度无任何日志）。
   真金白银入账必须留痕，判断为必要补充，不算越界。

6. 测试文件残留（N6 范围）：`model/payment_method_guard_test.go:76-79,155`、
   `model/task_cas_test.go:45-47`、`service/task_billing_test.go`、`model/subscription_promo_order_test.go`。
