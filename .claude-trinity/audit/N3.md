## 2. 响应体细节（给 N4 前端曹 / N6 对齐）

`GET /api/subscription/self` 新响应：

```json
{ "success": true, "message": "", "data": {
    "billing_preference": "wallet",
    "quota": 12345,
    "subscriptions": [],
    "all_subscriptions": []
} }
```

- `billing_preference` 取值改为常量 `service.BillingSourceWallet`（= `"wallet"`），
  与架构红线 4「`billing_source` 恒为 wallet」同一口径；**不再返回历史的
  `subscription_first` / `wallet_first` / `subscription_only` / `wallet_only`**。
- 新增 `quota` 字段 = `model.GetUserQuota(userId, false)`，即钱包余额。
- 两个列表是 `[]any{}`，序列化为 `[]` 而非 `null`（契约第 6 条）。

`PUT /api/subscription/self/preference` 恒返回 `{"success":true,"data":{"billing_preference":"wallet"}}`，
**不再解析请求体**（原 `BillingPreferenceRequest` 类型已删，避免留下解析了却不用的死代码）。

410 响应体沿用仓库既有形状（`success:false` + `message`），只是 HTTP 状态码是 410：

```json
{ "success": false, "message": "订阅额度池已下线，额度统一记入用户钱包余额，请改用 ..." }
```

由 `controller/subscription.go` 内的本地 helper `respondSubscriptionRetired` 统一构造。
`common/gin.go` 没有带状态码的响应 helper，且该文件不属于本轮任何一个曹，故未越界新增。

## 3. 🔴 移交事项：`MaxPurchasePerUser` 购买上限已从 controller 层移除

**这是本轮唯一的行为损失，必须有人接。**

5 个支付 controller（epay / stripe / creem / waffo_pancake / xunhu）原先都有一段
完全相同的预检，调用 `model.CountUserSubscriptionsByPlan(userId, plan.Id)`。
该函数内部查的是 `DB.Model(&UserSubscription{})` —— 属于 C8「删除 struct + 其全部函数」范围，
按分工要求「不保留调用、不建兼容垫片」，**5 处预检全部删除**。

- 这段预检本来就是**重复实现**：真正的事务内强制在
  `model/subscription.go` `CreateUserSubscriptionFromPlanTx`（原 :527-536）。删除它反而是收敛平行路径。
- **但 C6 要求 N2 把 `CreateUserSubscriptionFromPlanTx` 换成「加余额」，
  而 C6 的「必须保留」清单里没有列 `MaxPurchasePerUser`。**
  若 N2 不在新的加余额路径里补上这个上限判断，则**每档位限购 N 次这条业务规则整体失效**，
  用户可无限次购买设了上限的档位。
- 建议：N2 在加余额事务内改用 `SubscriptionOrder`（D1 保留）统计
  `user_id + plan_id + status = success` 的成功单数来做上限判断，
  `plan.MaxPurchasePerUser` 字段本身在 admin CRUD 里仍在校验、仍可配置，不能变成哑字段。
- 责任人：**N2**（新加余额路径）→ 若 N2 未处理则由 **N6** 收口时补。
