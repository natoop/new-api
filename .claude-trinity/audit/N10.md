## 1 · 索引怎么加的

`model/subscription.go` `SubscriptionOrder`，复用本仓既有的 GORM 复合索引写法
（`model/log.go:35-42` 的 `index;index:idx_xxx,priority:N`、`model/usedata.go:16-18`），
没有另起 `Migrator().CreateIndex` 之类的平行路径：

| 列 | tag |
|---|---|
| `UserId` | `index;index:idx_sub_order_user_plan_status,priority:1` |
| `PlanId` | `index;index:idx_sub_order_user_plan_status,priority:2` |
| `Status` | `index:idx_sub_order_user_plan_status,priority:3` |

列序与 `countPlanPurchasesTx` 的 `WHERE user_id = ? AND plan_id = ? AND status = ?` 逐列对齐——
这是锁范围能收窄的**唯一**前提，列序错了索引白建。已在 `countPlanPurchasesTx` 的注释里
写明这条耦合，并在测试里按列序（而非按索引名）断言。

**保留了 `UserId` 上原有的单列 `index`**，理由不是懒：GORM AutoMigrate 只建不删，
把 `index` 摘掉只会让新部署没有它、老部署继续留着，反而造成部署间 schema 分叉。
它对本轮结论无害（下面 §3 有分析），且 `ops_analytics.go:105` /
`distribution_order_sync.go:315` / `service/distribution_promotion.go:124` 也在按 `user_id` 查。

**纯加索引**：没加唯一约束、没做数据迁移、没动任何一行既有业务逻辑。

### 唯一一处被迫的列变更（MySQL 独有，且是索引可建的前提）

`Status` 原本无 gorm tag。GORM 的 MySQL dialector 对无 size 的 string 映射成 `longtext`，
而 **MySQL 拒绝给 longtext 建无前缀长度的索引**（1170 BLOB/TEXT used in key specification
without a key length）。绕法只有两条，一条走不通：

- 给索引加前缀长度（`index:...,length:N`）→ GORM 的 `BuildIndexOptions` 是 MySQL/PG 共用的，
  会把 `status(N)` 原样渲染进 PG 的 `CREATE INDEX`，PG 语法直接报错。**不可移植，否决**。
- 让 status 变成有界 varchar → 这正是 GORM 的既定行为：
  `gorm.io/driver/mysql@v1.4.3/mysql.go:370-393`，字段带 INDEX tag 且未指定 size 时取 `191`。

所以本轮只加 tag、**不加 `size:` / `type:`**，让三库各自取默认（见 §2）。
显式写 `size:64` 会连带把 PG 从 `text` 改成 `varchar(64)`，改的列反而更多，因此不写。

`status` 实际取值只有 `pending/success/failed/expired`（`common/constants.go:261-264`），
191 字符绰绰有余，`longtext → varchar(191)` 不存在截断。

## 2 · 三库兼容性确认（实测，非推断）

用 DryRun dialector（不连库）把三库的建表 DDL 各渲染一遍，实测结果：

| 库 | `status` 列 | 索引 DDL | 是否改列 |
|---|---|---|---|
| MySQL | `varchar(191)`（原 `longtext`） | `INDEX idx_sub_order_user_plan_status (user_id,plan_id,status)` 内联在 CREATE TABLE | **是**，且是索引可建的前提 |
| PostgreSQL | `text`（不变） | `CREATE INDEX IF NOT EXISTS "idx_sub_order_user_plan_status" ON "subscription_orders" ("user_id","plan_id","status")` | 否 |
| SQLite | `text`（不变） | `CREATE INDEX \`idx_sub_order_user_plan_status\` ON \`subscription_orders\`(...)` | 否 |

- PG dialector（`postgres@v1.5.2/postgres.go:190-194`）只在 `field.Size > 0` 时用 varchar，
  size 为 0 → 保持 `text`；PG 的 btree 索引 text 列没有长度限制问题（条目上限 ~2704B，status ≤ 8 字符）。
- SQLite dialector（`glebarez/sqlite@v1.9.0/sqlite.go:180-181`）对 `schema.String` 无条件返回 `text`，
  完全忽略 size/index tag。声明类型与现存类型一致 → GORM 不会触发 AlterColumn，
  **不会踩 CLAUDE.md Rule 2 里「SQLite 不支持 ALTER COLUMN」那条**。

### 迁移路径覆盖

`SubscriptionOrder` 早已同时在 `model/main.go:278`（`migrateDB`）与 `:345`（`migrateDBFast`）
的 AutoMigrate 名单里，**两条路径都无需额外改动**，加 tag 即自动生效。已确认。

顺序也是对的：`gorm@v1.25.2/migrator/migrator.go:103-180`，AutoMigrate 对已存在的表
**先 MigrateColumn（:143）再 CreateIndex**。所以存量 MySQL 库会先 `MODIFY COLUMN status varchar(191)`
再建索引，不会出现「拿 longtext 建索引失败」。MySQL migrator 的 `GetTypeAliases` 没有
longtext↔varchar 别名，所以这次 MODIFY 一定会触发（之后类型一致，不会每次启动重复 ALTER）。

### MySQL 索引键长限制

`8(bigint) + 8(bigint) + 191*4(utf8mb4) = 780` 字节。
DYNAMIC 行格式上限 3072B，够；COMPACT/REDUNDANT 上限 767B，不够。
本仓已有的 `idx_subscription_orders_trade_no` 建在 `varchar(255)` 上 = **1020 字节**，
早就越过 767 了 —— 也就是说本仓的 MySQL 部署本来就必须跑在 DYNAMIC（MySQL ≥ 5.7.9 默认）上，
本轮 780B 严格小于既有的 1020B，**不引入任何新的行格式要求**。

`subscription_orders` 只有几十条活跃单，建索引与 MODIFY COLUMN 的代价可忽略。

## 3 · 死锁复核 —— 完整推理

### 3.1 各路径改动后的实际锁序（重新逐行核对，不是抄 N9）

| 路径 | 真实持锁顺序 |
|---|---|
| 回调结算 `CompleteSubscriptionOrder` | `orders`(trade_no 单行 FOR UPDATE) → `users`(买家) → **`orders`(U,P,'success') 区间** → `users` UPDATE → `top_ups` → `orders` X 的 UPDATE → `p3_orders` |
| 余额购买 `PurchaseSubscriptionWithBalance` | `users` → **`orders`(U,P,'success') 区间** → INSERT `orders` |
| 库存码兑换 `service/distribution_transactions.go:765` | `users` → **`orders`(U,P,'success') 区间** → INSERT `orders` |
| `AdminBindSubscription` | `users` → **`orders`(U,P,'success') 区间** |
| `ExpireSubscriptionOrder` | `orders`(trade_no 单行) |

补一条 N9 没写、但对结论有影响的事实：`getSubscriptionPlanForUpdateTx`
（`model/subscription.go:325`）**名字带 ForUpdate 但没有任何 `clause.Locking`，实际不加锁**。
所以 `subscription_plans` 从头到尾没有被任何路径锁住，回调（plans→users）与余额
（users→...→plans）之间那个看起来的方向反转是假的，不参与成环。
`service/distribution_transactions.go:86` 的 `distributionLock` 同理（`gorm:query_option` 在
GORM v2 下是 no-op），`distribution_inventories` 也没有真锁。
这两处属存量假锁范畴，本轮按边界**未修**，仅记录 —— 它们不持锁，因此只会漏保护，不会造环。

### 3.2 收窄前为什么成环（N9 的两个场景，重新验证成立）

`user_id` 单列索引下，`SELECT ... FOR UPDATE WHERE user_id=U AND plan_id=P AND status='success'`
的索引扫描区间是 `user_id = U` 全段，`plan_id`/`status` 只能当回表后的过滤条件。
MySQL RR 下 **扫到即锁、不匹配也不放**（放锁是 READ COMMITTED 的行为），
所以该买家名下**所有**订单的聚簇记录都被锁住 —— 包含正在被回调事务持有的那张 pending 单 X。

于是：T1(回调) 持 X 等 `users` U；T2(余额/库存/AdminBind) 持 `users` U 等含 X 的区间 → 互等成环。
第二个场景（同用户两笔 pending 单的回调并发）同理。**N9 的判断成立。**

### 3.3 收窄后为什么不成环

加了 `(user_id, plan_id, status)` 之后，同一条 SQL 变成三列全等值匹配，
InnoDB 定位到 `(U,P,'success')` 这一个点区间并向后扫，加锁范围是：

1. 所有 `(U,P,'success')` 索引记录的 next-key 锁 + 对应聚簇记录锁；
2. 区间右边界那条不匹配记录的 next-key 锁（区间为空时退化为一个 gap 锁）。

关键推论：**pending 单不在这个范围里**。`status` 是索引第三列，
`'pending' < 'success'`（字典序，pending/failed/expired 全部排在 success 之前），
所以 `(U,P,'pending')` 落在扫描起点**之前**。区间起点那条记录的 next-key 锁只锁「它自己 + 它前面的间隙」，
不锁间隙前面那条记录本身。也就是说 X 的聚簇记录 **不会**被任何其他事务的限购 COUNT 锁到。

逐场景重新推：

**场景 1（回调 × 余额/库存/AdminBind，同一用户 U）**

- T1 = 订单 X 的回调，持有 X 的聚簇记录锁 + trade_no 索引记录锁，等 `users` U。
- T2 = 同用户的余额购买，持 `users` U，执行限购 COUNT。
  - T2 要锁的是 `(U,P,'success')` 点区间。X 的状态是 pending，索引条目在 `(U,P,'pending')`，
    **不在区间内 → T2 不会等 T1**。
  - T2 继续 INSERT 新订单，索引条目落在 `(U,P,'pending')`。这需要 insert intention 锁，
    只与 **gap 锁**冲突。T1 此刻手里只有 trade_no 上的等值记录锁（唯一索引等值匹配退化为纯记录锁，
    无 gap）和 X 的聚簇记录锁，**没有任何 gap 锁**（它还没走到 COUNT 就被 `users` 挡住了）→ 不冲突。
  - T2 一路提交，释放 `users` U。T1 拿到 `users` U 继续。
- 等待图里只剩 T1→T2 一条边，单边不成环。**环消失。**

**场景 2（同用户两笔 pending 单 X、Y 的回调并发）**

- T1 持 X 等 `users` U；T1′ 持 Y 且已拿到 `users` U。
- T1′ 的限购 COUNT 只锁 `(U,P,'success')`，X 是 pending → **不锁 X → T1′ 不等 T1**。
- T1′ 把 Y 翻成 success，这个 UPDATE 需要在索引里把 Y 的条目从 `(U,P,'pending')` 移到
  `(U,P,'success')`，即往自己刚锁住的区间里插 —— 是**自己的**锁，不冲突。
- T1′ 提交释放 `users` U，T1 继续。**环消失。**

**为什么不会有「T1 的 UPDATE 撞上别人的 gap 锁」**
T1 把 X 翻 success 时要往 `(U,P,'success')` 插索引条目，这确实会被别人的 gap 锁挡住。
但能持有该 gap 锁的必须是同一用户 U 的限购 COUNT，而那条路径**必须先拿 `users` U**——
`users` U 此刻在 T1 手里。`users` 行锁把同用户的所有路径完全串行化了，这个窗口打不开。

### 3.4 残余风险（如实记录，不粉饰）

1. **跨用户 gap 锁的理论环。** 当某用户该档位一笔成功单都没有时，COUNT 是空区间，
   InnoDB 会在右边界那条记录上加 gap 锁 —— 那条记录可能属于**另一个**用户。
   两个不同用户的事务若恰好互相锁住对方的插入间隙，理论上仍可成环。
   但这是任何二级索引区间锁都固有的 InnoDB 性质，不是本轮引入的；
   且锁范围从「整个 user_id 段」收到「一个点区间」后，命中概率是**严格下降**的
   （比 N9 之后低，也比 N9 之前的口径更窄）。触发还要求两用户索引条目相邻且无中间记录。
2. **优化器选择。** 结论成立的前提是 MySQL 真的选了新复合索引而不是老的 `user_id` 单列索引。
   三列全等值 ref（3 key parts）对一列等值 ref（1 key part），同表同代价模型下前者恒优，
   正常统计信息下不会选错。上线后建议对该 SQL 跑一次 `EXPLAIN` 落个实据；
   本轮**不加 `FORCE INDEX`** —— 那是 MySQL 专有语法，会破坏三库共用一份代码。
3. **PG / SQLite 无此问题。** PG 每语句取新快照、`FOR UPDATE` 不加 gap 锁；
   SQLite dialector 直接丢弃 Locking 子句、写本身串行。索引在这两库只是纯查询加速。

### 3.5 结论

N9 引入的两个同用户锁环，在 `(user_id, plan_id, status)` 复合索引下 **确定性消失**，
原因是 pending 订单行不再落进任何限购 COUNT 的加锁区间，
回调链路（orders→users）持有的那把「别人也想要的锁」不复存在，方向反转失去了成环的必要条件。
残余的只有 InnoDB 二级索引 gap 锁的通用性质（§3.4-1），概率严格低于改动前，不构成阻塞。
